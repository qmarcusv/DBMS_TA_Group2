The question

Same data, same SQL — why is one run instant and another slow?

Every role of the group studies one part of the engine through the same three queries. They look innocent, but each one stresses the database in a different way.

Q1 · point lookup

All scans of one patient

One diagnosis joined to its 65 slices. Cheap — if the database can find them without reading the whole table.

SELECT p.*, s.ScanID, s.ImagePath
FROM Patients p JOIN MRI_Scans s
  ON p.PatientID = s.PatientID
WHERE p.PatientID = '0001';
Q2 · filtered

Only the T2 sagittal sequences

Same as Q1 plus a LIKE '%T2%SAG%' filter — a pattern the optimizer can only guess at.

... WHERE p.PatientID = '0001'
  AND s.SeriesDescription
      LIKE '%T2%SAG%';
Q3 · similarity

The 3 most similar images

Euclidean distance between AI feature vectors across all 48,345 slices — a brute-force scan by nature.

SELECT TOP 3 s.ScanID,
  SQRT(SQUARE(f.V_Dim1-@T1)+ ... ) d
FROM Image_Features f JOIN MRI_Scans s ...
ORDER BY d;
Five angles on one engine

One role, one component of SQL Server, one headline result

Role 1 · Data
53 MB

Store file paths, not 13 GB of images. Bulk-load in 1.2 s; 48,345 AI vectors on a plain CPU.

Pipeline & schema → Role 2 · Index
−99.7 %

A covering index cuts Q1/Q2 from 1,880 to 6 page reads; columnstore for Q3.

Index design → Role 3 · Optimizer
3.4× cost

Force the "wrong" join and Q3 costs 3.4× more. Statistics, spills and cut-offs explained with real plans.

Plans & experiments → Role 4 · Transactions
All-or-nothing

Write-ahead log, rollback, crash recovery, and a durability trade-off that is 8.7× faster.

Log & recovery → Role 5 · Concurrency
7.9 s → 0

Locks, deadlock graphs and row versioning (RCSI): readers stop waiting for writers.
