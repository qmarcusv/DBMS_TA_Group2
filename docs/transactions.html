The mechanism

Write-ahead logging in one picture

A change is first described in the log, and the log reaches disk before the commit is acknowledged. Data pages can follow later — that is why SQL Server is fast and recoverable.

1 · UPDATE / INSERTpage changed in the buffer pool (dirty)
→
2 · Log recordwritten to the log buffer, gets an LSN
→
3 · COMMITlog flushed to disk first, then the client is told “done”
→
4 · Latercheckpoint / lazy writer flush the dirty data pages
Steal

Dirty pages may leave early

A page with uncommitted changes can be written to disk to free memory, so recovery needs an Undo pass.

No-force

Commit does not write data pages

Only the sequential log is forced at commit, so recovery needs a Redo pass. SQL Server runs Steal / No-Force (ARIES: analysis → redo → undo).

Experiment 2

Reading the log: an LSN is an address

Every log record has a 10-byte Log Sequence Number, shown in hexadecimal as VLF : page : slot, for example 00000030:0001517E:0002. Through sys.fn_dblog() we followed a transaction's chain: LOP_BEGIN_XACT → LOP_INSERT_ROWS → LOP_COMMIT_XACT, and for a rolled-back one the compensation records with backward Previous LSN pointers and LOP_ABORT_XACT.

The log file is a circle of Virtual Log Files (VLFs); a checkpoint writes dirty pages and lets the oldest VLFs be reused. The crash-recovery simulation verified the three ARIES phases against the log.

Beyond the slides

Durability is a dial, not a switch

How it worksCOMMIT … WITH (DELAYED_DURABILITY = ON) acknowledges the commit before the log block is flushed, so many commits share one write (log volume 20.6 MB → 3.8 MB). sp_flush_log forces the flush on demand.
The priceIf the server crashes before the flush, the last acknowledged commits are lost. That is acceptable for bulk loading, never for a diagnosis that a doctor has already been told was saved.
Checkpoint vs lazy writer

Performance counters show both background writers active during a workload: the checkpoint wrote 44 pages and the lazy writer 1,101. We only claim that both mechanisms exist and run; the counters do not isolate their effect.

In-Memory OLTP

Memory-optimised tables skip page latches and locks and log far less, at the price of RAM. Described in the report; not benchmarked.

What this provesSQL Server guarantees atomicity through the log, not through locks on data: even changes already made in memory are undone, and the log makes every commit durable before it is acknowledged.
